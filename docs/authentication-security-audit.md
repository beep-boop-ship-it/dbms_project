# Authentication and password security audit

## Password handling

- PostgreSQL login selects `password_hash` from the role-specific user table and verifies it in Go with `golang.org/x/crypto/bcrypt.CompareHashAndPassword`. Hash values are not copied to `domain.User` and are not returned by login/profile responses.
- PostgreSQL account columns use `text`, avoiding bcrypt hash truncation. Demo-mode credentials are now bcrypt hashes generated at process initialization with `bcrypt.GenerateFromPassword` at `bcrypt.DefaultCost`; each account gets a newly generated salt. Demo mode remains intentionally disposable and exposes the published demo password in the README.
- Seed accounts use distinct bcrypt cost-10 hashes generated by the same Go library. Verification SQL checks the bcrypt prefix and unique salts; the opt-in Go integration test authenticates each seeded role.
- No SQL trigger or SQL function handles passwords. No password is stored in PostgreSQL as plaintext.
- Signup, password-change, and password-reset routes do not exist in this application. Their hashing/reset behavior therefore cannot be audited as implemented; do not infer that account provisioning is available.
- Bcrypt cost 10 is the library default used by the current implementation. It is a valid password hash with per-hash random salt; tune the cost deliberately against deployment latency and migrate hashes if changing it.

## Session/token behavior

- The API creates a custom bearer token: base64url payload containing user ID, role, and expiry, signed with HMAC-SHA-256. It expires after 12 hours. Verification uses `hmac.Equal` and then reloads the user from the selected repository before each protected request, so the role is not trusted solely from client storage.
- Tokens are stored in browser `localStorage` and sent using the `Authorization: Bearer` header. There are no cookies, so `HttpOnly`, `Secure`, and `SameSite` cookie attributes do not apply. Local storage makes a stolen token accessible to injected JavaScript; a future session-hardening change should consider Secure, HttpOnly, SameSite cookies plus CSRF protections, or a short-lived token design with refresh/revocation.
- The token format has no issuer, audience, not-before, key ID, refresh, or revocation mechanism. A valid token remains usable until its 12-hour expiry unless the signing secret changes. This is a custom signed token format, not a standards-based JWT despite the `JWT_SECRET` configuration name.
- The development signing secret is accepted outside exact `APP_ENV=production`. Production validation checks only string length and exact environment spelling, not randomness. Configure a high-entropy secret and exact `APP_ENV=production` for deployed environments; consider making production mode an enum/case-normalized value and refusing known development secrets in every non-test deployment.
- Login has no rate limit, lockout, or audit event. Add protection at the API gateway or application before exposing a public login endpoint.

## Authorization and data exposure findings

- Role middleware protects the APIs, and room/session repository operations check teacher ownership. However, legacy `/students/me/attendance` and `/students/me/marks` return the shared `campus_state` arrays rather than records for the logged-in student. They also allow teacher and management roles. `/students/me/fees` returns one global fees object to all authorized students and management users.
- Legacy teacher `POST /attendance` and `POST /marks` update an aggregate row by course code. They do not verify that the teacher is assigned to that course. This is an integrity risk if these endpoints are used beyond the seeded/demo context.
- Library student issue history filters by the logged-in student's number in the JSON snapshot, but management issue creation and all records remain snapshot-based, without relational row-level ownership.
- The frontend stores a display role in `localStorage`; the API does not rely on it for authorization. API `auth` reloads the identity and compares its repository role with the signed token role.
- No endpoint returns `password_hash`, and current application logging does not log passwords, hashes, tokens, or `DATABASE_URL` values. Database connection errors are logged without printing the URL.

## Database-side security

The setup adds no access for Supabase `anon` or `authenticated` roles and does not enable RLS. The Go server connects directly as a trusted backend role and performs API authorization itself. Keep the PostgreSQL connection string only in server-side secrets, enforce TLS, use a least-privilege database role if the deployment has a workable role/grant setup, and do not expose it through `VITE_*` variables. If the backend changes to a non-owner role, add narrowly scoped grants and validate RLS behavior before enabling policies.

## Recommended follow-up before production

1. Scope student attendance, marks, and fee reads by the authenticated student; replace aggregate teacher mutation routes with offering-based, assignment-checked operations.
2. Move bearer tokens out of `localStorage` or reduce their impact with short lifetimes, refresh/revocation, and strong XSS controls.
3. Add login rate limiting and security audit events without recording secrets.
4. Add explicitly authenticated account provisioning and password update/reset flows that call bcrypt in Go; keep all seeded accounts development-only.
5. Review endpoint authorization and student ownership with production data before enabling the database for real users.
